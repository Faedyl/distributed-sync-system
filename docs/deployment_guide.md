# Deployment Guide

## Requirements

- Python 3.10+ (developed and tested on 3.11)
- Docker 24+ and Docker Compose v2 (for the containerized setup)
- ~150 MB free disk per node for write-ahead logs and snapshots
- Open TCP ports between nodes (default 8001 inside the overlay; mapped to 18011-18033 on host)

## Containerized run

```bash
cp .env.example .env
docker compose -f docker/docker-compose.yml --profile all up -d --build
```

Profiles:

- `--profile lock` — only the lock-manager cluster
- `--profile queue` — only the queue cluster
- `--profile cache` — only the cache cluster
- `--profile all` — everything

Verify:

```bash
for p in 18011 18021 18031; do
  echo "== $p =="
  curl -s http://127.0.0.1:$p/status | python -m json.tool
done
```

Tear down (preserving data):

```bash
docker compose -f docker/docker-compose.yml --profile all down
```

Wipe data:

```bash
docker compose -f docker/docker-compose.yml --profile all down -v
```

## Scaling

`docker/docker-compose.yml` is generated by `tools/gen_compose.py`. Regenerate with arbitrary counts to scale any cluster up or down — no hand-editing required:

```bash
# 5-node Raft lock cluster, 4-node queue, 3-node cache
python tools/gen_compose.py --lock 5 --queue 4 --cache 3 -o docker/docker-compose.yml

# odd numbers are recommended for Raft (3, 5, 7) — tolerates (n-1)/2 failures
docker compose -f docker/docker-compose.yml --profile all up -d --build
```

Other knobs:

| Flag | Default | Meaning |
| --- | --- | --- |
| `--lock N` | 3 | Lock-cluster Raft voters |
| `--queue N` | 3 | Queue cluster nodes |
| `--cache N` | 3 | Cache cluster nodes |
| `--queue-rf N` | 2 | Queue replication factor (clamped to ≤ `--queue`) |
| `--queue-vnodes N` | 128 | Virtual nodes per queue node on the hash ring |
| `--cache-capacity N` | 1024 | Per-node cache line capacity |
| `--cache-policy` | LRU | `LRU` or `LFU` |
| `--no-redis` | (off) | Omit the Redis sidecar |

To change topology in place:

1. Stop the running cluster: `docker compose -f docker/docker-compose.yml --profile all down`
2. Regenerate: `python tools/gen_compose.py --lock 5 ... -o docker/docker-compose.yml`
3. Bring it up: `docker compose -f docker/docker-compose.yml --profile all up -d --build`

`docker compose --scale` is **not** supported — each node has a unique `NODE_ID` and `PEERS` baked into its env, so the generator approach replaces it. With Raft (lock cluster), online membership change is also naive; production would require joint-consensus reconfiguration (out of scope).

## Environment variables

| Var | Required by | Description |
| --- | --- | --- |
| `NODE_ID` | all | Node identity (must match `PEERS`) |
| `NODE_BIND` | all | Bind address, e.g. `0.0.0.0:8001` |
| `PEERS` | all | Comma-separated `id@host:port` list including self |
| `DATA_DIR` | all | Persistent data directory |
| `LOG_LEVEL` | all | DEBUG / INFO / WARNING / ERROR |
| `RAFT_HEARTBEAT_MS` | lock | Default 120 |
| `RAFT_ELECTION_MIN_MS` | lock | Default 400 |
| `RAFT_ELECTION_MAX_MS` | lock | Default 800 |
| `QUEUE_REPLICATION_FACTOR` | queue | Default 2 |
| `QUEUE_VIRTUAL_NODES` | queue | Default 128 |
| `CACHE_CAPACITY` | cache | Default 1024 |
| `CACHE_POLICY` | cache | `LRU` (default) or `LFU` |
| `REDIS_URL` | optional | If set, available to components for shared metadata |

## Operational endpoints

| Path | Method | Notes |
| --- | --- | --- |
| `/healthz` | GET | Liveness probe |
| `/status` | GET | Component, peers, Raft role/term/leader (lock only) |
| `/metrics` | GET | Prometheus text exposition |
| `/metrics.json` | GET | JSON snapshot |

## Troubleshooting

**No Raft leader elected.**
Confirm all three lock nodes can reach each other on port 8001 (`docker exec lock1 curl -s lock2:8001/healthz`). Check that every node's `PEERS` includes the same three IDs in the same order. Election timeouts are randomized within `[RAFT_ELECTION_MIN_MS, RAFT_ELECTION_MAX_MS]`; if your environment has 100 ms+ inter-node latency, raise both values.

**`429 not leader` on every node.**
Indicates a partition or repeated election storm. Look at `/status` from each node — they should converge on a single `leader_id` within ~1s. If they don't, increase election timeouts (high jitter under load) or check clock skew.

**Queue drops messages on consumer crash.**
You probably set `visibility_ms` higher than the consumer's processing time. The visibility window is *exactly* what triggers redelivery. Tune accordingly, or add a heartbeat/extension mechanism on the consumer.

**Cache `state: S` after a single-node write.**
Means another peer still has a stale copy. That peer will discard its line on the next `BusRdX`, so the inconsistency is transient. Check your peer reachability if it persists — `cache_peer_unreachable` will be incrementing.

**Disk fills up.**
Queue WALs are append-only and never compacted in this implementation. For long-running workloads, periodically `docker compose down -v` between test runs or implement compaction (out of scope).

## Logs

Logs are JSON to stdout. Aggregate with:

```bash
docker compose -f docker/docker-compose.yml logs -f lock1 lock2 lock3 \
  | jq -c 'select(.level=="info" or .level=="error")'
```
